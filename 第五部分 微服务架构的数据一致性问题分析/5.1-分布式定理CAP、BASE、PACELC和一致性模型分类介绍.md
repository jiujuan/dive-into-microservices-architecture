## 一、分布式一致性的概念简介

在单机数据库里，一致性通常通过 ACID 事务保证：要么全做要么全不做，中间状态对别人不可见。

在分布式系统中，在一个由多台计算机（节点）组成的系统中，为了保证系统可靠性和性能，数据通常会有多个副本存储在不同的节点上。当数据更新时，如果所有副本不能同时、立刻更新，就会产生数据不一致的问题。

在分布式系统里，数据被复制到多台机器上会出现的问题，也就是数据为什么会不一致：
- 网络不稳定，可能出现分区（有些节点互相无法通信）
- 消息有延迟或丢失
- 计算机节点会突然宕机

分布式一致性描述的是，当更新操作完成之后，系统承诺所有用户在不同的节点上读取数据时，最终都能读到最新的值或者同一个确定的值。

简单例子说明：

假设有一个分布式数据库，数据 X 在节点 A、B、C 上各有一个副本。

- 1、初始状态，所有节点 X = 1。

- 2、客户端向节点 A 发送一个写请求，将 X 设置为 2。

- 3、节点A成功将 X 更新为 2。

现在，如果另一个客户端立刻去节点 B 读取 X，它会读到什么？

- 如果读到 2，说明系统是强一致性的。

- 如果读到 1，说明系统是弱一致性的，因为节点 B 的副本还没有同步到最新值。

分布式一致性就是用来解决这类问题的协议和理论。

> 分布式一致性就是在多节点、多副本、有网络延迟和故障的环境下，如何让不同节点对“同一份数据”的看法在某个维度上保持一致。

- 越强的一致性往往意味着更低的可用性或更高的延迟。
- 更高的可用性 / 更低的延迟往往意味着更弱的一致性（例如最终一致性）。

## 二、CAP 定理

CAP 定理（CAP Theorem），是分布式系统设计中的一个核心定理，由加州大学伯克利分校的Eric Brewer 于 2000 年提出，并于 2002 年由 Seth Gilbert 和 Nancy Lynch 正式证明。

CAP 定理指出，在分布式系统中，Consistency（一致性）、Availability（可用性）和 Partition Tolerance（分区容错性）三个属性无法同时满足，尤其在网络不可靠的环境下，在网络分区（Partition）发生时，系统必须在一致性（Consistency）和可用性（Availability）之间做出权衡，也就是说三个属性最多同时实现 2 个。

### CAP 定理核心概念说明

CAP 定理指出在分布式系统中，在网络故障不可避免的现实中，系统设计的取舍。定理的核心是：在网络分区发生时，系统只能保证其中两个属性。

- **C（Consistency）一致性**：所有节点在同一时刻看到最新的、相同的数据。任何读操作都能立即获取到最新的写操作结果。这就是线性一致性（linearizability），确保数据的全局一致。

- **A（Availability）可用性**：对系统中每一个非故障节点发起请求，系统必须在合理时间内返回一个响应，无论该响应是成功还是失败。即使部分节点故障，整个系统仍能提供服务。可用性强调的是系统对外服务的持续性和响应性，用户不应该因为系统内部的故障而长时间等待或无法获得服务。需要注意的是，可用性并不保证返回的数据是最新的，它只确保请求能够得到处理和回应。

- **P（Partition Tolerance）分区容错性**：系统在网络分区发生时，即节点之间网络通信中断，即两个节点都正常运行但无法相互通信。在真实的网络环境中，网络故障是不可避免的，如路由器故障、网络延迟、网络丢包等导致节点间的通信中断，系统仍能继续对外提供服务。分布式系统必须具备分区容错性，因为网络故障在现实中不可避免。

>说明： **线性一致性**（linearizability）是 CAP 中的 C 的原始定义。很多人在谈到 CAP 时，会把这个 C 看成是 **强一致性**（strong consistency）。这其实也没错，因为线性一致性的另一个名字，就是强一致性。
### CAP 定理三选二

在现实选择中，分区（P）不可避免时，因此 P 必须满足，
- 选择 C（一致性） 则牺牲 A（可用性）（系统可能拒绝请求以确保一致）；
- 选择 A（可用性）则牺牲 C（一致性）（允许节点返回旧数据）。

因此，设计系统时实际上是在 **C（一致性）** 和 **A（可用性）** 之间做出选择。

- **CA（放弃 P，一致性+可用性）**：保证强一致性和可用性，但无法容忍网络分区。这意味着系统所有节点必须时刻保持连通，**这在分布式系统中几乎不可能实现**，所以 CA 系统通常只存在于单机系统中，所有数据都存储在单个节点上，不存在网络分区的问题。这种系统虽然能够提供完美的一致性和可用性，但缺乏分布式系统的扩展性和容错能力。

- **CP（放弃 A，一致性+分区容错性）**：优先保证一致性和网络分区容错性，牺牲了可用性。在发生分区时，为了保证数据在所有节点上的一致性，系统可能会拒绝部分用户的写或读请求，直到数据同步完成。

   一些典型的系统：ZooKeeper, Etcd, HBase, MongoDB（配置为强一致性时）。
   
   使用场景：对数据准确性要求极高的场景。比如金融系统余额、支付系统、电商库存数量扣减等。

- **AP（放弃 C，可用性+分区容错性）**：保证可用性和网络分区容错性，但牺牲了强一致性，允许系统在网络分区时返回可能不一致的数据。当发生网络分区时，系统仍然提供服务，但不同节点返回的数据可能不是最新的（即存在数据不一致的窗口期），但会通过事后操作修复来达到最终一致性。

   一些典型的系统：许多 NoSQL 和分布式 KV 存储，如 Cassandra、DynamoDB 的最终一致性（弱一致性）配置等。
   
   使用场景：对可用性要求高，可以容忍短暂数据不一致的场景，如社交媒体的点赞数、日志分析、评论、用户行为埋点数据等。

> 说明：AWS 的 DynamoDB 支持多种一致性模型，主要包括**最终一致性**和**强一致性**，以及用于多个项目或任务操作的**事务性一致性**，全局表还能实现**多区域强一致性**，确保全局读取最新数据。
> 使用哪种一致性模型只需要对 DynamoDB 进行配置。


### CAP 定理的局限性

尽管 CAP 定理为分布式系统设计提供了重要的理论指导，但它也存在一些局限性。

首先，CAP 定理中的"一致性"和"可用性"的定义相对绝对化，在实际系统中往往存在灰度空间。

例如，系统可以在大部分情况下保证强一致性，仅在网络分区时降级为弱一致性；系统可以在大部分时间内保证高可用性，仅在极端情况下降低响应速度。

其次，CAP 定理主要考虑的是网络分区这一种故障模式，而实际分布式系统还面临节点崩溃、时钟偏移、消息延迟等多种复杂情况。
等等情况促使了后续 PACELC 等理论的提出和发展。

## 三、BASE 理论

### BASE 理论介绍

BASE 理论是对 CAP 定理中 AP 方向的补充和拓展。它告诉我们，在放弃强一致性（C）后，系统应该如何设计来提供“足够好”的服务。

它是针对大规模分布式系统提出，来自 eBay 的架构实践。它强调可用性和分区容忍性，牺牲强一致性换取性能、可用性、扩展性。
许多互联网应用，如电子商务、社交网络、在线游戏等，对可用性和性能的要求远高于对强一致性的要求。这些应用可以容忍短暂的数据不一致，只要最终数据能够正确同步即可。BASE 理论为这类应用提供了理论支撑和设计指南，使得系统能够在保证基本可用的前提下，通过最终一致性机制实现数据的最终同步。

BASE 的含义：

- **BA - Basically Available（基本可用）**：系统整体可用，即使部分节点故障，分布式系统绝大部分时间都可以响应请求，允许短暂降级、限流、部分功能不可用，不追求 100% 严格可用。

- **S – Soft state（软状态）**：系统中的数据状态可以存在“中间状态数据”、“临时状态数据”，且这个中间状态数据不影响系统的整体可用性，允许不同副本数据在一段时间内存在不一致，随时间推移而收敛到一致。

- **E – Eventually consistent（最终一致性）**：保证如果没有新写入，经过一段时间数据同步后，所有副本最终会达到数据一致的状态，但过程中可能出现不一致。这个一段时间被称为”不一致窗口“。

上面有举例了一些典型的系统如 Cassandra 系统、DynamoDB 的最终一致性（弱一致性）配置等，还有使用场景对可用性要求高、性能要求高，但可以容忍短暂数据不一致的场景，如社交媒体的点赞数、日志分析、评论、用户行为埋点数据等。


### 使用场景

BASE 理论适用于多种实际业务场景。

比如，

在内容分发系统（CDN）中，用户上传的内容需要同步到全球各地的边缘节点，这个过程天然具有延迟性，采用最终一致性是合理的选择。

在社交网络系统中，用户发布的动态信息、点赞、评论、朋友圈等操作可以立即返回成功，但其他用户可能需要等待几秒钟才能看到这些更新。

BASE 理论并非要完全放弃一致性，而是提供了一种更加务实的权衡策略。
在实际应用中，开发者可以根据业务需求，将 BASE 理论与传统的 ACID 事务相结合，在关键业务环节使用强一致性保证，在非关键环节使用最终一致性以换取性能和可用性的提升。

## 四、PACELC 定理

### PACELC 定理介绍

PACELC（由 Daniel Abadi 在 2010 年提出）是对 CAP 的扩展和补充，它指出了一个的问题：CAP 只讨论了发生网络分区（P）时在 C 和 A 之间的选择，但系统大部分时间都运行在无网络分区（即网络正常）的状态下，那时我们又怎么权衡？

>PACELC 是 "Partition（分区）、Else（否则）、Latency（延迟）、Consistency（一致性）"四个概念首字母的缩写。

PACELC 定理包含两个决策点，完整地描述了分布式系统在两种情况下的权衡关系。定理表述为：

- PAC 部分，在发生网络分区（P）时，系统要在可用性（A）和一致性（C）之间做出选择——这点与 CAP 相同。

- ELC 部分，否则（Else，E），即在“没有发生网络分区”的常规情况下，系统要在延迟（L，Latency）和一致性（C）之间做出选择。

也就是说，除了故障场景下的 可用性（A）vs 一致性（C），我们还得考虑正常情况下的延迟性（L） vs 一致性（C）。

这个定理揭示了在分布式系统中，即使在没有网络故障的理想情况下，一致性（C） vs 性能（延迟 L）也是一对天生的矛盾。

- 要保证强一致性，就必须增加节点间的通信和协调，这必然会增加请求的响应时间（高延迟）。 比如你可以让写操作必须同步到多数副本才返回成功，从而得到更强一致性，但延迟更高。

- 要追求低延迟，就可能需要减少节点间的协调，允许数据异步复制，这就牺牲了一致性。比如你让写操作只在本地/少数副本成功就返回，再在后台异步复制，从而延迟更低，但一致性变弱。


### 分类与使用场景


根据 PACELC，可以对数据库进行更精细的分类：

1. **PC/EC**（优先一致性，无分区时也优先一致性）：当发生分区（P）时选择一致性（C），在无分区时（E）也选择一致性（C）。即**永远优先保证一致性**。
    - **数据库场景**：传统的 CP 系统，如 etcd、HBase,、BigTable。它们追求最强的一致性保证，通常延迟也较高。
        
2. **PC/EL**（优先一致性，无分区时优先低延迟）：当发生分区（P）时选择一致性（C），但在无分区时（E）选择低延迟（L）。这是一个有趣的组合，它在正常情况下通过优化（如从主节点读取）来降低延迟，但在关键时刻（分区时）仍然保证一致性。
    - **数据库场景**：MongoDB（可调一致性）, Redis（主从模式），还有Google Spanner在正常情况下追求低延迟，同时通过 TrueTime 等技术保证强一致性。
        
3. **PA/EL**（优先可用性，无分区时优先低延迟）：当发生分区（P）时选择可用性（A），在无分区时（E）选择低延迟（L）。即**永远优先保证可用性和低延迟**。
    - **数据库场景**：DynamoDB（可配置）, Cassandra, Voldemort。它们是典型的AP系统，通过牺牲一致性来获得极高的可用性和性能，但可能返回稍旧的数据。

4. **PA/EC**（优先可用性，无分区时优先一致性）：理论上存在，但实践中较少。因为如果在无分区时都能保证强一致性（EC），那么在分区时通常很难做到真正的可用性（PA）。这种组合相对少见，因为它意味着系统在正常和异常情况下采取完全不同的策略，实现复杂度较高。

## 六、分布式一致性模型分类

根据一致性强度的不同，分布式一致性模型可以大致分类为**强一致性模型**、**弱一致性模型**和**最终一致性模型**（后者常视为弱一致性的子类）。

### 强一致性模型

强一致性模型（Strong Consistency Models），这种模型要求系统表现得像单一节点一样，所有操作立即可见，且符合严格的顺序。它们提供高的数据准确性，但往往需要同步数据机制，导致延迟高和可用性低。

它又可分为线性一致性模型和顺序一致性模型。

1、**线性一致性模型（Linearizability）**

线性一致性是最强一致性模型，所有操作都有全局唯一的真实时间顺序（real-time order），每个操作看起来都在单一时间点原子性的执行完成，操作顺序必须与真实时间的先后顺序一致。就像只有一个全局的时间机器，所有操作按“绝对时间”排序。读操作总是返回最新的写结果。比如分布式锁，Google Spanner。

特点：全局时序一致，延迟高、实现成本高。


2、**顺序一致性模型（Sequential Consistency）**

它比线性一致性稍弱。

顺序一致性，所有操作按照程序顺序（program order）执行，即要求所有处理器看到的写入顺序是一致的，且每个处理器的操作顺序符合其程序顺序（program order），但不强制要求绝对真实时间顺序。

例如 A 先写 X=1，后写 Y=2；其他节点可能过了一会儿才看到，但它们看到的顺序绝对是先 X=1 后 Y=2，绝不会反过来。比如 Java 内存模型 (volatile),。

它与线性一性质模型的区别：不要求与真实时间顺序一致。可以在某个全局顺序中执行。


### 弱一致性模型

弱一致性模型（Weak Consistency Models），这种模型放松了强一致性的要求，允许临时不一致，以换取更好的性能和可用性。它们不保证立即可见性，但提供某些特定保证。

它的分类如下：

1、**因果一致性（Causal Consistency）**

因果一致性就是有因果关系的操作顺序必须一致，无因果关系是可以乱序。

例如操作 A 和操作 B 有因果关系（例如 B 是回复 A 的评论），那么所有节点必须先看到 A，再看到 B。
如果没有因果关系（并发），则节点看到的顺序可以不同。无关操作可能乱序。比如社交网络中的评论系统。


2、**会话一致性（Session Consistency）**

在单个会话（如客户端连接）内保持一致性。比如某一客户端在自己的会话中看到自己所有写操作的结果，不同会话之间可能有不一致。


3、**单调一致性（Monotonic Consistency）**

单调一致性严格来说是一组**一致性保证（Guarantees）**。

- **单调读一致性**（Monotonic Reads Consistency，不会越读越旧），如果一个用户读取了某个数据的新版本，他后续的读取绝对不会看到更旧的版本。比如用户多次读取操作，数据的版本只能保持不变或变得更新，而不会回退到更早的版本。

- **单调写一致性**（Monotonic Writes Consistency，写有序）。同一个用户的多个写操作按照它们发起的顺序执行，不会出现乱序。这种一致性模型确保了写操作的串行化，防止了并发写操作导致的数据异常。


### 最终一致性模型

最终一致性模型（Eventual Consistency Models），这是一种特殊的弱一致性，不保证任何中间数据状态的一致，但保证如果系统不再有更新，承诺系统最终会数据收敛到一致状态。它是分布式系统中（如 NoSQL 数据库）最常见的模型，强调可用性和分区容忍性（参考CAP定理）。

1、**基本最终一致性**

在没有新更新的情况下，最终所有读取会返回相同的值。

中间数据状态不一致的窗口时间可能有秒级到分钟级的时间不等。

典型的场景就是 DNS 系统、CDN内容分发、Cassandra 数据库。


2、**读自己的写一致性（Read-Your-Writes Consistency）**

读自己的写一致性是一种会话级别的一致性模型，它保证一个用户提交写操作后，总是能够读取到自己写入的数据。

这种一致性模型在用户体验层面非常重要，因为用户通常期望能够立即看到自己刚刚执行的操作结果，即使系统在其他方面可能存在不一致。例如，当用户更新了自己的头像后，立即刷新页面应该能够看到新头像；当用户发布一条动态后，刷新 timeline 应该能够立即看到这条动态信息。


## 七、总结

分布式一致性理论是设计和实现可靠分布式系统的理论基础。

CAP 定理揭示了在一致性和可用性之间不可调和的矛盾，为系统架构设计提供了重要的指导原则。

BASE 理论提供了一种务实的替代方案，通过基本可用、软状态和最终一致性，允许系统在保证核心功能可用的前提下，通过异步同步实现数据的最终一致。

PACELC 定理进一步扩展了 CAP 理论，将正常运行时的延迟与一致性权衡纳入考量，提供了更加全面的分布式系统设计指导原则。

一致性模型从强一致性到最终一致性，形成了一个适应不同场景的选择。强一致性提供最强的一致性保证，但性能和可用性相对较低；

最终一致性提供最好的性能和可用性，但需要业务层面处理数据不一致的情况。因果一致性、读自己的写一致性、单调读一致性等模型则在不同维度上提供了一致性保证，满足不同场景的需求。

在实际系统设计中，需要根据业务需求、性能要求和系统复杂度，选择合适的一致性策略。不同的系统组件可以采用不同的策略，关键业务采用强一致性保证，非关键业务采用最终一致性以换取性能提升。

首先是业务需求，不同的业务场景对一致性的要求不同。金融交易系统需要强一致性，而社交网络的 feed 流则可以接受最终一致性。其次是性能要求，更强的一致性通常意味着更高的延迟和更低的吞吐量，系统需要在一致性和性能之间找到平衡。再次是系统复杂度，更强的一致性模型通常需要更复杂的协议和更多的协调开销。

分布式缓存系统是一致性理论的一个重要应用场景。缓存系统的设计目标是在提供快速响应的同时，尽可能保证数据的一致性。Redis Cluster 采用异步复制机制，在主节点写入数据后异步同步到从节点。这种设计保证了主节点的写入性能，但可能导致短暂的数据不一致。在主从切换时，可能丢失最近的写入操作。Redis 通过 WAIT 命令提供了同步复制选项，允许用户强制等待指定数量的从节点确认复制完成。

现代分布式数据库和存储系统通常提供多级别的一致性选项，使得开发者能够灵活地在一致性和性能之间进行权衡，构建出既可靠又高效的分布式系统。例如，Amazon DynamoDB 提供强一致性、最终一致性和事务一致性三种选项；Apache Cassandra 提供 QUORUM、ALL、LOCAL_QUORUM 等多种一致性级别。这种灵活性使得开发者可以根据具体操作的需求选择合适的一致性级别，在性能和正确性之间取得最佳平衡。
